## What runs

### VQC mechanism and tiny decision example

[`backend/quantum_learning.py`](../backend/quantum_learning.py) is a two-qubit, exact local statevector circuit. It encodes normalized input features with `RY(pi*x0)` on q0 and `RY(pi*x1)` on q1, applies `CNOT(0,1)`, trainable rotations `RY(theta0)` and `RY(theta1)`, then `CNOT(1,0)`. The readout is the fixed Pauli observable `Z0`; predicted event risk is `p = sigmoid(-2 <Z0>)`. Circuit metadata reports 2 qubits, depth 4, four RY gates and two CNOT gates. It is a standard-library CPU simulator, not a QpiAI VQC call or finite-shot estimate.

For the saved example `x=(0.2,0.8)`, `theta=(0.31,-0.47)`:

1. Feature angles are `0.6283` and `2.5133` radians.
2. The simulator returns `<Z0> = -0.563024`; the readout gives `p = 0.755109`.
3. The soft decision compares estimated costs `A = 2+4p = 5.0204` and `B = 3.1+4(1-p) = 4.0796`. At temperature 1, route shares are `A = 0.280724`, `B = 0.719276`.
4. For synthetic event label `y=1`, the realized toy costs are `A=6`, `B=3.1`; the share-weighted value is `3.914101`.

The generic decision-loss gradient on eight fixed training examples is analytic `[0.4704903084, 0.0626290562]`; centered finite differences at `h=1e-5` are `[0.4704903085, 0.0626290562]`, maximum absolute error `5.31e-11` (tolerance `2e-7`). The gradient is propagated through the circuit using parameter shift for `<Z0>`, then the sigmoid and soft decision loss. The prospective route-dispatch objective also has a nonzero circuit gradient: analytic `[0.8809412569,-0.4045884433]`, finite difference `[0.8809412567,-0.4045884435]`, maximum error `2.04e-10` on scenarios `prospective-00` and `prospective-02`.

The example is a smooth two-route training surrogate. It does not model a complete operational fleet objective. In the generic circuit, `Z0` is fixed: trainable parameters are in the gate ansatz, not a trainable observable/readout layer.

### Decision-focused route dispatch and comparison

[`backend/prospective_dispatch.py`](../backend/prospective_dispatch.py) implements the forecast-separated prospective experiment; [`backend/learning_dispatch.py`](../backend/learning_dispatch.py) is the earlier diagnostic pipeline. Prospective features are forecast route travel duration and nominal contractual-window pressure. A route estimate is `forecast travel duration + p * sum(order penalty rates) * 1 minute`. The one-minute severity is an explicit, uncalibrated proxy. For each scenario, a temperature-2 soft minimum over validator-approved plans differentiably weights their independently recomputed realized objectives. The validator separately recomputes order coverage, vehicle use, capacity, ordered timing, lateness, travel cost, and objective.

The prospective simulation protocol was frozen before its evaluation: SHA-256 `60CDC7A0B6E676B2BE9FFA7928BC0BE505BBF9870B9D65CF48D833F935AD86F8`. It uses 24 synthetic grouped scenarios (12 train, 6 validation, 6 test), separate forecast and realized matrices, and common random numbers for all three methods. The model sees forecast input only; realized values are opened after route selection. The six test cases are too few for uncertainty estimates or calibration conclusions.

Every method chose the same plans (`V1: B -> C`, `V2: A`) on all six cases. Optimizer budgets were unequal: the VQC methods used 120 updates each; logistic regression used 500. Synthetic proxy units are not currency, and estimated exposure was not calibrated.

The earlier diagnostic integration used realized scenario travel as both model input and validator outcome. Its results are not prospective forecasting evidence. ### QUBO, Ising, and warm-start QAOA

In [`backend/qubo.py`](../backend/qubo.py), bit `x_i` selects candidate route `i` in input order. The objective is route cost plus exact stop-coverage penalties and pairwise at-most-one-route-per-vehicle penalties:

`E(x) = sum_i cost_i*x_i + Pcov*sum_s(sum_{i covers s} x_i - 1)^2 + Pveh*sum_v sum_{i<j on v} x_i*x_j`.

The vehicle term allows a vehicle to receive no route. For the four-route synthetic example (`A_ab:4`, `A_a:2`, `B_b:2`, `C_ab:5`, coverage penalty 20, vehicle penalty 15), variable order is `[A_ab,A_a,B_b,C_ab]`. Expanding gives offset `40`, linear coefficients `[-36,-18,-18,-35]`, and nonzero upper terms `(0,1)=55`, `(0,2)=40`, `(0,3)=80`, `(1,3)=40`, `(2,3)=40`. Selecting only `A_ab` has energy 4 and independently recomputed business cost 4.

With `z=1-2x`, `backend/qubo.py::qubo_to_ising` returns `E=c+sum_i h_i*z_i+sum_ij J_ij*z_i*z_j`, including the constant. The same example gives `c=50.25`, `h=[-25.75,-14.75,-11,-22.5]`, with `J` equal to each listed quadratic coefficient divided by four. The local test exhaustively equates QUBO and Ising energy for every assignment. A circuit regression also checks each computational-basis amplitude against `exp(-i*gamma*E(x))`, so the Ising constant is preserved in phase evolution.

`backend/qaoa.py` uses a deterministic projected-gradient box relaxation initialized at `x=0.5`; it is not an LP solver. Each relaxed `p_i` initializes `sqrt(1-p_i)|0> + sqrt(p_i)|1>`. Its warm mixer is `(2*sqrt(p_i*(1-p_i)))X + (1-2p_i)Z`; for `p=0.25`, the initial state `[sqrt(0.75),0.5]` is its `+1` eigenstate. The standard path starts uniformly with X mixers. Both run one layer on a common angle grid with a shared sampling seed and shot budget. Every raw bitstring, QUBO validation, repair edit, and repaired validation is kept separately. The dispatcher accepts only a raw sample that also passes the domain validator; otherwise the exact classical fallback is labeled as such.

The custom local comparison used the four-route fixture, 10x10 angle grid, seed 20261028 and 512 shots per method: standard QAOA had 231 feasible samples; warm-start had 384. Both best raw feasible samples cost 4.0, equal to the exact tiny reference. These are sample counts from a synthetic pure-Python local statevector, not evidence of superiority.

### QpiAI local SDK execution

[`backend/qpiai_adapter.py`](../backend/qpiai_adapter.py) creates the route-selection `Model`/`QUBOProblem`, passes a continuous-relaxation vector to `WarmStart`, builds QAOA, and calls QpiAI Quantum `StatevectorSimulator`. The tested SDK environment used QpiAI Opt 0.0.9 and QpiAI Quantum 0.3.0. The SDK objective terms plus offset matched the source route QUBO for all 256 assignments in the eight-variable fixture. A 2,048-shot asymmetric-probability probe verified that SDK count strings are reversed relative to variable order. In the subsequent 128-shot warm-start run, 11 samples passed both QUBO checks and the independent domain validator. The selected raw result decoded to `V2: B -> A`, objective 4.0, and validator `valid=true`.

The adapter is limited to eight variables because compiled-index and output-order checks were executed only through that size. No QpiAI Opt `Client.solve`, authenticated service, cloud simulator, QCloud, or QPU job ran. No credentials were read or submitted.

### Risk scoring and recovery audit

[`backend/risk.py`](../backend/risk.py) and `POST /api/v1/risk/evaluate` replay a fixed plan across 1–100 explicit travel matrices, independently validate each replay, and report finite-sample event/stop/order frequencies, mean proxy costs, optional fractional-tail CVaR, and hashes. Actual localhost check at `127.0.0.1:18376` used two repeated matrices with distinct IDs: both validators were true, late frequency was 0, expected proxy objective was 10, and CVaR at 0.75 was 10. The server was stopped. These are supplied-scenario empirical summaries, not calibrated probabilities or a forecast model.

Recovery audits are stored append-only in SQLite only after input and result validation. They retain validated source inputs, plan, locked prefixes, stable result/failure, timestamps and hashes. Latest successful plans are keyed to the original scenario/plan scope; a failed attempt does not replace that scope's last success. Recovery search bounds remain 2,000 route candidates and 10,000 recursive nodes. It replays from depot/time zero, without live vehicle location, clock, or operational state.
